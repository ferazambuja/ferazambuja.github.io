Color measurement and rendering for a six-state e-paper display

An experimental ICC workflow, controlled color-prediction tests, and an image renderer informed by measured native colors.

Making intermediate colors with six pixel states

I have long been fascinated by how e-paper forms images with reflective pigments. This project uses a Pimoroni Inky Impression 7.3-inch Spectra 6 module and its image-conversion software as a starting point.

Unlike conventional RGB control, this controller interface gives each pixel one of six native states. A renderer creates intermediate colors by distributing those states across neighboring pixels: halftoning, also called dithering. The pattern is part of how the image makes color.

The diagrams show digital controls, not measured display appearance. Under simple area averaging, the measured yellow and blue endpoints predict a muted, low-chroma color rather than paint-mixing green. A physical pattern can depart from that simple estimate.

An experimental profile improved the measured color grid

I first added an ICC color conversion before the unchanged Pimoroni renderer. The profile described an experimental rendering-and-display setup; the conversion changed the RGB values handed to the renderer and therefore the native pixels it chose.

Equal color counts could produce different measured colors

While evaluating the display, I found that horizontal and vertical blue/green patterns with identical color counts gave different readings. Tests of other pairs revealed larger differences, including the black/yellow example below.

A pixel payload is the digital instruction that assigns a native state to every pixel. It is not a forecast of the light the display will reflect. I chose the test patterns directly and checked the sent state maps, so ordinary image conversion was not choosing different pixels behind the comparison.

A larger difference: the black/yellow patterns

The two curves show how much light each horizontal and vertical pattern reflected at each wavelength. The lower curve shows their wavelength-by-wavelength difference. The accompanying color coordinates and distances describe different parts of the same result.

Reading this example: the spectrum records reflected light across wavelengths. From it, XYZ describes color under a specified illuminant and observer; Lab expresses that color as lightness (L*), green–red (a*) and blue–yellow (b*) coordinates. CIEDE2000 (ΔE00) summarizes how far apart the two colors are. RMS instead summarizes the size of their spectral difference, and pp means percentage points of reflectance factor.

Pattern and prediction results use D50, the CIE 1931 2° observer, and Lab relative to a nominal perfect-diffuser D50. The ICC grid instead uses panel white as its reference, so values from the two conventions should not be compared directly.

Here, H means horizontal and V means vertical. H minus V keeps the direction: a positive L* difference means H measured lighter, positive a* means redder, and positive b* means yellower. Repeated readings show how much each pattern changed over time.

The effect was not limited to horizontal and vertical stripes

Three colors, unchanged stripe direction

Grouping black, yellow and blue rows changed measured color even when both patterns remained horizontal. Cyclic versus grouped measured 15.39 ΔE00, and the contrast returned at 15.57 ΔE00 when I reversed the reading order.

The same region in a different surrounding image

Would the same pixels measure the same color inside a picture and against a white background? The outlined 64 × 64 pixels below are identical in both images; only their surroundings change.

These are the exact digital pixel maps sent to the display, not photographs or simulations of the measured colors. The outline marks the pixels kept unchanged, not the meter's measurement area.

Same center pixels, different readings

The average measured colors differed by 3.23 ΔE00.

On repeating: I measured the image twice and the white-background version twice. Comparing each image reading with each white-background reading gives four pairings, with a largest difference of 3.33 ΔE00. Those pairings reuse the same four readings; they are not four separate experiments.

Why the cause is still open: The meter collects light from an area, not a single pixel. I measured the patterns, but did not map how much each part of the screen contributed to its signal. This comparison therefore cannot tell us whether the difference came from the surrounding image changing the display's response, the way the meter collected light, or changes during the measurement sequence.

An image renderer with explicit color choices

The measurements made pixel selection an engineering question, not just an image-conversion step. I built an offline renderer that interprets source color, uses measured native-state references, and produces exact display pixels. Its current route works without a learned prediction model.

Software previews, not panel photographs. Both pixel maps are recolored with the same visualization palette: the measured native-state colors used for the ICC artwork previews, scaled so the panel's white appears white. This palette is only for comparing pixel choices; it is not the renderer's endpoint-reference table and does not predict panel appearance or optical improvement. Both renderers receive the same interpreted, fitted source; this is not Pimoroni's untouched image-intake workflow.

I tested one change to how color error is passed to neighboring pixels across 114 fixed software conditions. It made the average slightly worse and introduced tone and detail regressions, so I kept the existing Floyd–Steinberg default. That is a software design decision, not a claim of better measured screen color.

Some forecasts succeeded within their tested conditions

Forecasts saved before measurement met the selected error limit on all eight readings of two exact patterns. Two empirical forecasts also succeeded on all four readings of one new four-color raster. Those were real, bounded prediction successes.

The illustration below shows a separate successful forecast. It also explains a different problem: knowing what color will be produced is not the same as producing the color we wanted.

On six regions in three new images, a learned rule reduced error on all 12 readings compared with an additive baseline, but neither method met the selected limit on any reading. Across the tested patterns, occurrences and image regions, reliable absolute-color prediction was not established. Some misses persisted when repeated measurements agreed closely, so they cannot all be explained by display instability.

What the project produced

The project produced three connected results: an experimental ICC route that lowered mean error on a 133-color grid, controlled measurements showing when pixel organization and image surroundings changed readings, hold/redraw and return tests on identical pixels, and an offline renderer that turns images into exact native-state pixels with explicit color and halftoning choices.

Forecasts worked in narrow cases but did not transfer reliably, so the renderer's current default does not depend on them. The open question is how far the measured pattern behavior can support a more general display model.
